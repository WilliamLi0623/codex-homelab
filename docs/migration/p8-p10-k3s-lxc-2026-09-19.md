# P8-P10 K3s/LXC migration evidence

This is an infrastructure evidence record for the V3 migration. It is not a
general installation guide. It intentionally omits private addresses,
credentials, tokens, and host-specific key paths.

## P8: control plane

- Proxmox LXC220 `k3s-control` was created from Ubuntu 24.04 with
  `unprivileged=1`, `nesting=1`, 4 CPUs, 8 GiB RAM, and a 32 GiB rootfs.
- No host mount, Docker socket, device passthrough, or privileged LXC setting
  was used.
- K3s is pinned in `versions.lock` as `v1.37.0+k3s1` (commit `95f479b`).
- The tagged installer was downloaded and recorded with SHA256
  `ed01f89fd977bf20ac1516bbebf8370bf3ddbaa55dac8aba610956a4c78cc00b`.
- K3s systemd service is enabled and active. The control-plane node reported
  `Ready` and the required `codex-control=true:NoSchedule` taint.

## P9: three disposable worker cycles

Each worker used Ubuntu 24.04, an unprivileged LXC, `nesting=1`, the pinned
K3s release, and no host resource mounts. Each joined the control plane and
successfully ran a BusyBox Pod with a worker Pod IP, cluster DNS resolution,
and TCP reachability to the Kubernetes service.

- LXC3001 passed the compatibility checks. Its first teardown exposed a
  lifecycle defect: stopping a worker before cordon/drain leaves system Pods
  on a dead Node. The stale Node was removed and CoreDNS was recovered on the
  next worker.
- LXC3002 passed after the recovery. It was then cordoned, drained, stopped,
  and its Kubernetes Node was removed.
- LXC3003 passed after the corrected lifecycle order. It was cordoned,
  drained, stopped, and its Kubernetes Node was removed.
- After the explicit cleanup confirmation, LXC3001, LXC3002, and LXC3003 were
  destroyed with `--purge`. Protected guests were not modified.

The lifecycle rule for future workers is therefore: persist the claim, cordon,
drain, remove the Kubernetes Node, stop the LXC, and only then destroy it.

## P10: secret-free template

- LXC3004 is the stopped build source for the template.
- LXC3005 is the full clone marked as the Proxmox template
  `codex-k3s-agent-template`.
- The template contains Ubuntu 24.04, systemd, the pinned K3s Agent binary,
  container runtime support, and diagnostics (`curl`, `jq`, `dnsutils`, ping,
  netcat, and procps).
- The K3s agent service is disabled and inactive in the template; its runtime
  environment file is zero bytes, and no cluster URL or join token was
  injected.
- Scans found no CC Hub, OpenAI, GitHub, Proxmox, or K3s token markers, no
  K3s server token/config, and no root-home key/token files.

P11 must inject a fresh, scoped join configuration at claim time rather than
placing credentials in this template.

## Storage placement update

The V3 storage rule is that system rootfs volumes use SSD-backed `local`, while
only data volumes use the mechanical `pool` storage.

- LXC220 was stopped cleanly, moved from `pool` to `local`, verified, and
  restarted. Its K3s service and control-plane node returned to `Ready`.
- LXC3004 and the LXC3005 template were moved from `pool` to `local`; neither
  has a data mount.
- LXC210 remains running with its rootfs on `pool` and is intentionally not
  included in this evidence until its separate protected-resource maintenance
  approval is explicit.
