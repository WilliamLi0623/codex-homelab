## Release lifecycle checkpoint

- `internal/capacity.ReleaseWorker` now provides and tests the mandatory
  destructive-release ordering: cordon, drain, remove and verify the
  Kubernetes node, verify Proxmox identity, stop and verify stopped, then
  destroy.
- The boundary rejects protected VMIDs, missing identity, and UNKNOWN state;
  it stops on any error, including `ErrUnknown`, and does not retry or infer
  external progress.
- This is a tested ordering boundary only. It is not yet wired to the
  production CapacityAdapter/runtime or a durable release-progress ledger, so
  dynamic worker destruction remains closed.
- The SQLite `release_progress` migration and store API now provide an
  idempotent identity-bound checkpoint ledger with forward-only steps and
  explicit `UNKNOWN` persistence. The production release adapter still does
  not consume it, so no external release is enabled by this change.
- The capacity runner now supports resuming after a durably completed release
  step and checkpoints successful/UNKNOWN outcomes. `CapacityAdapter.Release`
  accepts this path only when an explicitly injected, identity-aware
  `WorkerReleaseOperations` implementation is present; the current production
  environment does not inject one, so remote destruction remains closed.
- UNKNOWN release checkpoints now require an explicit identity-bound
  `ReconcileRelease` call with an observation proof before the current step
  can be retried; normal `Release` calls cannot clear UNKNOWN implicitly.
- Dynamic capacity claims now derive a deterministic DNS-safe worker identity
  (`codex-lxc-<vmid>-<generation-prefix>`) from the persisted VMID and
  generation. Completion and release paths use the same derivation instead of
  relying on a static or empty hostname.
- Capacity create requests now carry deterministic ownership metadata and the
  Proxmox adapter encodes it in the clone description in stable key order.
  Metadata is tested locally; live guest metadata verification is still a
  migration gate.
- `ProxmoxRuntime.VerifyIdentity` now performs a read-only exact VMID,
  deterministic hostname, and required metadata check against the LXC config;
  mismatches fail closed. This verifier is tested but is not yet connected to
  a live release operation set.
- The K3s runtime now exposes tested cordon, drain, Node deletion, and
  Node-absence verification operations. Drain leaves mirror and DaemonSet
  Pods to their controllers and waits for ordinary Pods to disappear; these
  operations remain injectable and are not active in the current Controller.
- `orchestrator.ReleaseOperations` now composes those K3s operations with
  Proxmox identity, stop, stopped-observation, and destroy boundaries while
  preserving the mandatory order. Missing sub-boundaries fail closed; the
  production Controller still does not inject this destructive set.
- `ResultConsumer.ObserveAndComplete` now provides a tested observer boundary:
  pending/running jobs remain incomplete, failed/cancelled jobs fail closed,
  and only a succeeded job enters the existing commit-SHA and durable
  completion path. A scheduler/background loop and live Job watch are still
  not configured.
- Dispatch now persists an attempt-bound deterministic branch and validation
  command in SQLite before invoking the external dispatcher. A restarted
  controller can use `ObserveAndCompleteStored` without reconstructing these
  values from memory; missing or conflicting specs fail closed.
- The production Controller composition now starts a bounded observation loop
  with a cancellable lifecycle. It polls persisted specs every five seconds
  and shuts down with the Controller; live external Job/commit evidence is
  still required before P13 can pass.
