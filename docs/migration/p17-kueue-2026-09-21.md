# P17 Kueue admission checkpoint — 2026-09-21

## Decision

Kueue is the admission layer for the K3s worker Jobs. The production controller
uses the explicit `default` LocalQueue in namespace `codex`; Jobs opt in with
the `kueue.x-k8s.io/queue-name` label. The worker container declares CPU and
memory requests so Kueue can account for the workload.

Responses/Muse failover remains deferred. Current worker routing stays
`glm-5.3-flash` over Chat Completions.

## Checked-in resources

`deploy/kueue/codex-queues.yaml` defines:

- `ResourceFlavor/default-flavor` for the homogeneous K3s worker nodes;
- `ClusterQueue/codex` with a 4 CPU / 8 GiB nominal quota;
- `LocalQueue/default` in namespace `codex`.

The controller environment variables are:

```text
KUEUE_QUEUE_NAME=default
KUBERNETES_CPU_REQUEST=500m
KUBERNETES_MEMORY_REQUEST=512Mi
KUBERNETES_CPU_LIMIT=1
KUBERNETES_MEMORY_LIMIT=1Gi
```

The runtime keeps the previous no-queue behavior when `KUEUE_QUEUE_NAME` is
unset. When a queue is configured, it fails closed unless CPU and memory
requests are present and valid; partial limits are rejected.

## Release lifecycle evidence

The same live worker release was reconciled after the operator verified VMID
3040 stopped and the Kubernetes Node absent. The durable release ledger now
records:

```text
task=task-832106566092fb867685069f7ac0acf3
attempt=attempt-f4ac41a8dfe72ad0e6d5a4b1d2725663
vmid=3040
step=DONE
state=COMPLETED
```

The observed external end state is also explicit: Proxmox reports no
`3040.conf`, and K3s returns `NotFound` for the deterministic worker Node.

The blocker exposed three production/test mismatches, all fixed and covered
by regression tests:

- Proxmox `/lxc/<vmid>/config` does not include a `vmid` field; the request path
  is already VMID-scoped, so an omitted field is accepted while a non-zero
  returned field must still match.
- Proxmox descriptions include one trailing newline; metadata decoding now
  accepts that terminator while continuing to reject empty fields and unsafe
  values.
- Proxmox returns HTTP 500 when `STOP` is sent to an already stopped CT;
  `Stop` now observes first and treats `NodeStopped` as idempotent success.

Separately, new dynamic nodes do not yet inherit the local worker image; P19
must make image import/bootstrap deterministic instead of relying on manual
import.

The existing `deploy/worker/Prepare-AgentRuntime.ps1` only stages the
`codex-agentd` binary. It does not preload an OCI image. A live-node check
confirmed that the stopped Proxmox template has no running K3s/containerd
socket, while a claimed worker imports the image into
`/run/k3s/containerd/containerd.sock`. Therefore P19 needs an explicit image
preload mode (or a shared registry/mirror); merely copying `codex-agentd` into
the template is insufficient.

The checked-in `deploy/kubernetes/codex-controller-node-rbac.yaml` grants only
the node lifecycle verbs required by the existing Cordon/Drain/RemoveNode
implementation. It was applied before the successful release reconciliation.

## Release reconciliation control surface

The controller now exposes a dedicated endpoint for an operator or recovery
automation to reconcile a durable release record:

```text
POST /v1/tasks/{task}/attempts/{attempt}/release/reconcile
```

`codexctl reconcile-release` is the matching CLI command. The endpoint loads
the durable capacity claim and release-progress row itself, requires the row
to be `UNKNOWN`, and requires the supplied VMID, generation, and Kubernetes
node name to match the stored identity. It only changes the current step back
to `PENDING`; it cannot directly request `STOP` or `DESTROY`. The endpoint and
CLI have regression tests for identity mismatch, missing proof, and non-UNKNOWN
state. The deployed Controller includes the release retry, identity diagnostics,
Proxmox config compatibility, metadata trailing-newline, and idempotent STOP
fixes; its verified Linux artifact SHA-256 is
`aa94a418e7dcb31bd66e1f4f84274750adb111a0f7bda8a81c33d8700160494b`.
